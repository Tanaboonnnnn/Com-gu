## Method and scope

This was a destination/process-ownership observation only. TLS was not intercepted, credentials were not printed for the verification, and no production service was attacked. Candidate instances used isolated Electron user-data directories. TCP ownership was sampled with Windows `Get-NetTCPConnection` and correlated with process paths/PIDs. Scratch captures under `.runtime-egress/` are intentionally untracked; this report records the durable evidence and limitations.

The candidate was built with `npm run build` and `npm run dist:x64`. `smoke-packaged-core.mjs` passed 3/3 runs and `smoke-packaged-runtime.mjs` reported the expected Electron/native runtime (`electron 43.4.1`, `sharp 0.35.3`, node-pty available, tree-sitter program parse available).

## Idle

Observed from `2026-09-07T16:06:00+07:00` through `16:07:57+07:00` (28 samples, about 117 seconds) with Goal disabled and no usable tunnel configuration in the isolated profile.

**Result:** no outbound TCP connection was observed from the candidate `ComGu.exe` process tree. No `tunnel-client.exe` or `cloudflared.exe` child was present. This also proves there was no OpenRouter traffic while Goal was off during the observation window.

A separate startup capture observed `ComGu.exe -> 20.205.243.168:443`; DNS resolution identified that address as `api.github.com`, matching the documented background update check.

## Extension-only bridge

Observed from `2026-09-07T16:23:34+07:00` through `16:24:17+07:00` using an isolated profile, a test-only bridge token, and the exact test extension origin `chrome-extension://aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa`. A protected bridge request succeeded (`protectedRouteOk: true`).

**Result:** the only connection owned by the candidate during this feature exercise was loopback `127.0.0.1`. No remote destination was observed. This matches the policy that the companion extension talks to Desktop over the local bridge only.

## OpenAI MCP tunnel

A functional auto-connect observation ran from `2026-09-07T16:14:21+07:00` through `16:16:06+07:00` (24 samples). The packaged candidate spawned two packaged `tunnel-client.exe` children, corresponding to the Core and Desktop surfaces. Both established TLS connections to `172.66.0.243:443`. Inspection of the pinned packaged tunnel-client binary showed the expected OpenAI control-plane strings including `api.openai.com` and `mtls.api.openai.com`.

The main `ComGu.exe` also contacted `20.205.243.168:443`, identified as `api.github.com`, for the normal update check.

**Capture limitation:** this successful tunnel run reused the installed profile's real tunnel IDs so it could exercise a valid data-plane connection. That allowed live MCP session traffic to reach the candidate during the observation and caused command/session child processes to appear in the accumulated process tree. Their traffic is therefore not treated as independent app-managed egress evidence. A follow-up isolated run used syntactically valid but nonexistent tunnel IDs to avoid that data-plane overlap; the control-plane client exited too quickly to be sampled. No additional app-managed destination was discovered. Future release verification should prefer disposable OpenAI tunnel IDs when the control plane provides a safe way to create them.

The OpenAI result is accepted for destination ownership because the remote TLS endpoint was owned by the packaged `tunnel-client.exe` processes, while the only separate main-process remote endpoint was independently attributed to GitHub update checking.

## Cloudflare quick tunnel

**NOT RUN.** The Cloudflare adapter was not selected or exercised during this Windows candidate session. No `cloudflared.exe` process was present in the idle or extension-only observations. Cloudflare remains a documented, user-selected native tunnel trust boundary and is not required to be exercised by this plan when it is not explicitly selected.

## Goal / OpenRouter

The packaged candidate was launched with an isolated profile and auto-connect disabled. A disposable invalid OpenRouter key was written through the packaged renderer's normal `setGoalKey` IPC path. The bridge `/goal/open` route was then invoked repeatedly with the non-sensitive text `runtime egress verification only`; the expected upstream failure was returned as HTTP 502 because the disposable key was invalid.

During those requests, the candidate main process established TLS to `104.18.3.115:443`. DNS resolution for `openrouter.ai` returned `104.18.2.115` and `104.18.3.115` at verification time. The only other observed connection was loopback bridge traffic.

**Result:** PASS. Goal traffic went to the documented OpenRouter destination; no unrelated app-managed remote destination appeared.

## Conclusion

The packaged Windows x64 candidate's observed app-managed destinations match `docs/security/egress-policy.md`: GitHub for update checking, the pinned OpenAI tunnel client for MCP tunnel transport, loopback-only extension bridge traffic, and OpenRouter only when Goal was explicitly exercised. No product analytics, crash-reporting, webhook, advertising, or unexplained app-managed endpoint was observed. Cloudflare was not exercised and is recorded as **NOT RUN**, not inferred as passing.
